# Architectural decision record (ADR) 017: toolchain-aware adapter fallback diagnostics

## Status

Accepted (2026-08-15): keep fatal macro-error handling in `proc-macro-error3`,
and use toolchain-specific emission for first-party adapter fallback warnings.

## Date

2026-08-15.

## Context and problem statement

The scenario macros resolve `harness` and `attributes` paths to the base
`rstest-bdd-harness` API when a path looks like a first-party adapter but its
crate cannot be resolved. This includes a local re-export or a renamed
dependency. Silently selecting the base API leaves users without an explanation
or a remedy.

The compiler warning APIs differ by toolchain. Nightly can emit a native
procedural-macro diagnostic, while stable procedural macros cannot emit a
warning directly. The implementation also needs to preserve the existing fatal
macro-error boundary and must not emit one fallback warning for every test
generated by `scenarios!`.

## Decision drivers

- Keep fatal parse and validation failures behind one maintained macro-error
  boundary.
- Give nightly users a native, correctly spanned warning.
- Give stable users the same actionable guidance, including support for
  `#![deny(deprecated)]`.
- Make resolution side-effect free so each expansion boundary owns emission
  and the warning cardinality is deterministic.
- Keep canonical first-party paths and unrelated third-party adapters
  warning-free.

## Decision outcome

`proc-macro-error3` remains the macro crate's fatal-error support. The `abort!`
call sites and the `entry_point` and `proc_macro_error` wrapper in
`run_with_macro_errors` map panics and fatal macro diagnostics; they do not
emit adapter fallback warnings.

Adapter resolution is a pure decision. `resolve_harness_api` returns the
selected base API path and optional fallback metadata. The expansion boundary
then emits that metadata once and reuses the resolution for runtime code, trait
assertions, and generated output. `#[scenario]` owns its own boundary;
`scenarios!` resolves before iterating feature scenarios and shares the result
with every generated test. Therefore each distinct qualifying supplied
`harness` or `attributes` path emits exactly one diagnostic, regardless of the
number of generated scenarios. The two supplied paths remain independent.

On nightly, the boundary calls `proc_macro::Diagnostic::spanned` with
`proc_macro::Level::Warning` and emits it directly. On stable, the macro
generates a deprecated unit-item reference carrying the same message. Stable
therefore reports a deprecation warning by default, and `#![deny(deprecated)]`
promotes it to an error. These paths are mutually exclusive.

`proc-macro-error2` is not reintroduced for this warning. Its warning path is
unavailable on stable, which is the toolchain that requires the generated
deprecation diagnostic. Review also identified it as unmaintained. Adding it
would duplicate the macro-error dependency surface without providing the
required stable warning channel, while splitting warning behaviour away from
the direct nightly diagnostic boundary.

## Rationale

The warning is an expansion-level fact, so its owner must be the expansion
boundary rather than each generated scenario. Keeping resolution pure makes
that ownership explicit and prevents nightly's side-effecting
`Diagnostic::emit()` call from being repeated. The stable marker is the
smallest compiler-supported way to carry equivalent guidance through a stable
procedural macro, and the deprecation lint gives projects an opt-in strict mode.

Keeping `proc-macro-error3` for fatal errors preserves the existing panic and
`syn` error handling without making it responsible for a warning mechanism it
cannot provide consistently across the supported toolchains.

## Options considered

### Reintroduce `proc-macro-error2` for fallback warnings

Rejected: its warning emission does not provide the required stable warning
channel, so the generated deprecation path would still be necessary. It would
also reintroduce a second macro-error API for a concern already handled by the
toolchain-aware boundary.

### Emit the fallback from every generated scenario

Rejected: a feature directory with multiple scenarios would repeat the same
diagnostic. Stable compiler output can hide identical deprecation markers, but
nightly native emission remains a repeated side effect.

### Use only the generated deprecation marker on every toolchain

Rejected: nightly has a native diagnostic API with the correct source span;
using the stable workaround there would discard that channel and make the two
toolchains less consistent with their capabilities.

## Consequences

- Fatal macro errors continue to use `proc-macro-error3`; adapter fallback
  warnings stay in `codegen::adapter_fallback`.
- Changes to fallback resolution must preserve pure resolution and one
  diagnostic per distinct qualifying supplied path.
- Stable and nightly user-interface fixtures must keep the shared diagnostic
  text and mutually exclusive emission paths aligned.
- Canonical first-party paths and custom adapters with the same type name do
  not produce fallback diagnostics.

## Verification coverage

Unit tests cover pure resolution for aliased, canonical, and custom adapter
paths, one or two diagnostics at the expansion boundary, and no diagnostic when
a generated scenario reuses shared resolutions. Tokio `trybuild` fixtures cover
stable alias and combined-path failures, while nightly fixtures cover the
native alias warning and a two-scenario `scenarios!` expansion. Canonical pass
fixtures run through the same stable/nightly harness, and the nightly fixtures
pin exactly one native warning, including a multi-scenario expansion.
