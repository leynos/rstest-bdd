# Annotate step parameters with `#[harness_context]` (roadmap 11.2.1)

This ExecPlan (execution plan) is a living document. The sections `Constraints`,
`Tolerances`, `Risks`, `Progress`, `Surprises & discoveries`, `Decision log`,
and `Outcomes & retrospective` must be kept up to date as work proceeds.

Status: DRAFT

## Purpose / big picture

Today, a step definition that wants the harness-provided context object must
spell a reserved fixture key by hand:

```rust,no_run
#[when("I record the GPUI test context")]
fn record_gpui_test_context(
    #[from(rstest_bdd_harness_context)] context: &gpui::TestAppContext,
) {
    let _ = context.test_function_name();
}
```

`rstest_bdd_harness_context` is an implementation detail: it is the string key
under which the framework stores `HarnessAdapter::Context` in the per-step
`StepContext` fixture map. Users must know and correctly type a 27-character
internal identifier in order to reach a first-class feature. Adopters of the
v0.6.0 beta line reported this as a friction point.

After this change, the same step reads:

```rust,no_run
#[when("I record the GPUI test context")]
fn record_gpui_test_context(#[harness_context] context: &gpui::TestAppContext) {
    let _ = context.test_function_name();
}
```

The reserved key does not disappear. It stays exactly where it is, inside
generated code, and the old spelling keeps working unchanged. This is a v0.6.1
additive-hardening change: purely additive, semver-compatible, no removals.

You can observe success three ways:

1. A step function annotated `#[harness_context]` receives the harness context
   at runtime, proved by a passing behavioural scenario in
   `examples/tokio-reminders`.
2. The two spellings generate byte-identical wrapper code, proved by a unit
   test comparing token streams.
3. Misuse produces targeted compiler diagnostics rather than a bare
   `cannot find attribute` error, proved by `trybuild` compile-fail fixtures.

Roadmap entry 11.2.1 in `docs/roadmap.md` (line 981) is the requirement of
record. Its finish line is: *"macro tests cover both marker forms and examples
compile using `#[harness_context]`."* Roadmap 11.2.2 (prelude exports) and
12.2.1 (typed `Harness<T>` extractors) both build on this work; neither is in
scope here.

## Constraints

Hard invariants. Violating one requires escalation, not a workaround.

- **Semver compatibility.** v0.6.1 must stay compatible with v0.6.0. Do not
  remove, rename, or change the signature of any public item. In particular
  `rstest_bdd::RSTEST_BDD_HARNESS_CONTEXT_FIXTURE` must remain a
  `pub const … : &str` with the value `"rstest_bdd_harness_context"`, and
  `#[from(rstest_bdd_harness_context)]` must keep working with no deprecation
  warning.
- **No proc-macro dependency cycle.** `crates/rstest-bdd-macros` must not
  depend on `crates/rstest-bdd`. This is stated normatively in
  `docs/developers-guide.md` under "Workspace dependency policy" (lines 26-32).
  Shared values belong in `rstest-bdd-patterns`, `rstest-bdd-policy`, or
  `rstest-bdd-harness`.
- **400-line file limit.** No Rust source file may exceed 400 lines. Enforced
  by `scripts/check_rs_file_lengths.py`, which runs inside `make lint`. Several
  files this plan touches are already close to the ceiling; see "Context and
  orientation". An allowlist exists at `scripts/rs-length-allowlist.txt`, but
  it is headed "Temporary exemptions while large modules are refactored" and
  tracked for removal under issue #50. Do not add an entry for new code.
- **Directory-based module roots.** A module that has children lives in
  `<name>/mod.rs`, not `<name>.rs` beside a `<name>/` directory. The workspace
  migrated wholesale to this layout in commit `3e6c367` ("Adopt directory-based
  Rust modules", #651). New modules must follow it.
- **Do not edit `typos.toml` by hand.** It is generated by
  `scripts/generate_typos_config.py`.
- **en-GB-oxendict spelling** in all prose, comments, and documentation
  (`-ize`, `-yse`, `-our`, `-re`). Code identifiers keep upstream spelling.
- **Markdown wrapping:** paragraphs and bullets at 80 columns, fenced code at
  120 columns, tables and headings unwrapped.
- **No `unsafe`.** The workspace forbids it.
- **No `.expect()` or `.unwrap()` in production code.** Whitaker's
  `no_expect_outside_tests` and `no_unwrap_or_else_panic` lints enforce this in
  `make lint`. Tests are exempt: `clippy.toml` sets `allow-expect-in-tests` and
  `allow-panic-in-tests`, and `AGENTS.md` was amended in commit `3e6c367` to
  say tests may consume a fallible `rstest` fixture with `.expect(...)` rather
  than returning `Result` purely to propagate a setup error. The exemption does
  not reach helpers outside `#[cfg(test)]` or `#[test]`.

Stop and escalate — do not improvise — when any of these is reached.

- **Interface:** any change to an existing public function or type signature
  beyond adding new items. Adding `HARNESS_CONTEXT_FIXTURE` to

  without restructuring code outside this plan's scope, stop and escalate.
- **Ambiguity:** if the reviewer's intent for the marker's interaction with
  `#[step_args]`, `#[datatable]`, or step-pattern placeholders differs from the
  behaviour specified in "Plan of work", stop and present options.

## Risks

- **Risk:** the `#[harness_context]` marker leaks into generated code on a path
  where no classifier strips it, producing an opaque
  `error: cannot find attribute 'harness_context' in this scope`. Severity:
  high. Likelihood: medium. Mitigation: strip the marker unconditionally and
  early, before the placeholder short-circuit in `extract_args`; add
  compile-fail fixtures for every combination that could otherwise leak (with
  `#[step_args]`, with `#[datatable]`, on a placeholder-named parameter, on a
  `#[scenario]` function).

- **Risk:** file-length ceiling breached. `classify/mod.rs` is 382/400 lines and
  `classify/tests.rs` is 384/400. Adding to either fails `make lint`. Severity:
  medium. Likelihood: high if not planned for. Mitigation: the plan places all
  new classifier code and its tests in new modules under
  `classify/harness_context/`.

- **Risk:** `googletest` is new to this workspace, so its interaction with the
  local lint configuration is unproven — in particular Clippy under
  `-D warnings` and the Whitaker suite, both of which see macro-expanded test
  code. Severity: low. Likelihood: medium. Mitigation: Milestone 2 lands the
  dependencies and a throwaway `#[rstest] #[googletest::test]` smoke test on
  their own, gated, before any real test depends on them, so a lint clash
  surfaces in isolation rather than tangled with the classifier work.

- **Risk:** `googletest`'s `proptest` integration does not behave as documented
  under this workspace's `default-features = false` pin of `proptest`.
  Severity: low. Likelihood: low. Mitigation: the property test falls back to
  `prop_assert!` with an explicit message after one failed attempt, and the
  deviation is recorded in `Surprises & discoveries`. The unit tests do not
  depend on this integration.

- **Risk:** `googletest`'s minimum supported Rust version exceeds this
  workspace's `rust-version = "1.85"`. Severity: medium if it occurs, because
  it would block adoption outright. Likelihood: low. Mitigation: check before
  pinning in Milestone 2; if it does exceed, escalate rather than raising the
  workspace MSRV as a side effect of a test-tooling change.

- **Risk:** `pretty_assertions::assert_eq!` shadows the `std` macro, so a
  module-wide import silently changes the behaviour of existing assertions in
  that module. Severity: low. Likelihood: low. Mitigation: the new tests live
  in new modules, so nothing pre-existing is shadowed; import it per module
  rather than at crate root.

- **Risk:** `syn::Ident::new` panics on a non-identifier string, and the
  reserved key now arrives from another crate's constant. Severity: low.
  Likelihood: low. Mitigation: a unit test asserting `HARNESS_CONTEXT_FIXTURE`
  parses as a `syn::Ident`, plus a comment at the construction site recording
  the invariant.

- **Risk:** GPUI example builds are slow or platform-sensitive, lengthening the
  feedback loop when validating the migrated example. Severity: low.
  Likelihood: medium. Mitigation: the primary behavioural test lives in the
  lighter `examples/tokio-reminders` crate; the GPUI example migration is
  verified with a scoped `cargo test -p gpui-counter` before the full gate run.

- **Risk:** `trybuild` `.stderr` snapshots drift with compiler version.
  Severity: low. Likelihood: low. Mitigation: generate `.stderr` files with
  `TRYBUILD=overwrite` on the pinned toolchain in `rust-toolchain.toml`, and
  review them rather than accepting blind.

## Surprises & discoveries

- Observation: the Tokio harness's step wrapper polls an async step future at
  most once when a harness-provided runtime is active (`emit/mod.rs` uses a
  noop waker and rejects `Pending`), so a step that `.await`s a spawned task or
  `flush()` fails with "multi-poll async steps are not supported under a
  harness". The behavioural scenario therefore proves marker reachability
  synchronously (comparing `context.handle().id()` with
  `tokio::runtime::Handle::current().id()`, the same identity check the
  harness's own integration tests use) and dispatches via a new synchronous
  `ReminderService::deliver_all`, which polls each immediately-ready queued
  task once. Date: 2026-08-17.

- Observation: the parameter-named spelling
  (`fn s(rstest_bdd_harness_context: &TestCtx)`) cannot be compared for full
  structural equality with the marker spelling, because the two `Arg::Fixture`
  entries differ in the *span* of the synthesized identifier. The reserved-key
  contract is the fixture *name*, not the span, so the Milestone 3 test for
  that spelling asserts the resolved names rather than `ExtractedArgs`
  equality. Date: 2026-08-17.

- Observation: the `#[step_args]` cross-guard in `classify_step_struct` must
  run before `validate_has_placeholders`, otherwise
  `#[harness_context] #[step_args] c: &C` with an empty placeholder set reports
  "requires at least one placeholder" instead of the targeted combination
  diagnostic. The guard order moved `validate_no_from_attr` and the new
  `validate_harness_context_attr` ahead of the placeholder-count check; the
  existing `classify_step_struct` tests still pass because they use either
  non-empty placeholder sets or bare `#[step_args]`. Date: 2026-08-17.

- Observation: googletest's `matches_pattern!` requires an explicit `..`
  terminator when the pattern omits fields, even for `pub` enum variant fields.
  The illustrative examples in this plan's Milestone 3 omit `..`; the committed
  tests include it. The `..` carries no semantic weight for omitted fields
  (each is matched as `anything()`), it is purely a rustc pattern-privacy
  requirement surfaced by the macro expansion. Date: 2026-08-17.

- Observation: the runtime crate and the macro crate are coupled to the
  reserved fixture key *only through the literal text a user types*. There is
  no shared constant. Evidence: `crates/rstest-bdd/src/context/mod.rs:46`
  defines `RSTEST_BDD_HARNESS_CONTEXT_FIXTURE`; a repository-wide search finds
  no reference to that constant, or to the string, anywhere in
  `crates/rstest-bdd-macros/src`. The macro crate emits `stringify!(#name)`
  where `#name` is whatever identifier the user wrote inside `#[from(...)]`.
  Impact: `#[harness_context]` must synthesize the identifier itself, so the
  coupling becomes real and must be made drift-proof. Milestone 1 exists for
  this reason.

- Observation: `extract_args` skips the special-argument classifiers entirely
  when the parameter name matches a step-pattern placeholder. Evidence:
  `crates/rstest-bdd-macros/src/codegen/wrapper/args/extract.rs` lines 170-173.
  Impact: a naive insertion of the new classifier into
  `classify_special_argument` would let `#[harness_context] count: &Ctx` leak
  the marker when the pattern contains `{count}`. The new classifier therefore
  runs before that short-circuit.

- Observation: the branch was rebased onto `origin/main` at commit `3e6c367`
  on 2026-08-16, picking up a workspace-wide migration to directory-based
  module roots. The rebase was textually clean — this branch adds only one new

## Decision log

- Decision: `#[harness_context]` is an inert bare marker attribute consumed and
  stripped by `#[given]` / `#[when]` / `#[then]`, not an exported attribute
  macro. Rationale: this matches the in-repo precedent for `#[datatable]` and
  `#[step_args]`, and the upstream precedent set by `rstest` itself, whose
  `#[from]`, `#[case]`, `#[with]`, `#[default]`, and `#[future]` markers are
  likewise consumed by the enclosing attribute macro and are not exported items
  (confirmed against the `rstest` 0.26.1 crate root, which exports only
  `rstest`, `fixture`, and `Context`). Whether the marker should additionally
  be re-exported from a prelude is roadmap item 11.2.2's decision, not this
  one. Date/Author: 2026-08-15, planning agent.

- Decision: the reserved fixture key moves to a single definition in
  `crates/rstest-bdd-policy`, with `rstest-bdd` keeping its existing public
  constant as an alias. Rationale: the macro crate must not depend on
  `rstest-bdd`, and `rstest-bdd-policy` exists precisely to "centralize …
  definitions so both the runtime crate and the proc-macro crate can depend on
  a single, canonical definition without creating a proc-macro dependency
  cycle" (its own module documentation). Duplicating the string literal in the
  macro crate would leave the two free to drift silently. Alternatives
  rejected: a private constant in `rstest-bdd-macros` guarded by a cross-crate
  equality test (weaker: the test can be deleted, and the failure mode is a
  confusing runtime missing-fixture error); `rstest-bdd-patterns` (owns pattern
  parsing, not policy); `rstest-bdd-harness` (only a *dev*-dependency of
  `rstest-bdd`, so unusable from its runtime code). Date/Author: 2026-08-15,
  planning agent.

- Decision: the new classifier runs first, unconditionally, before the
  placeholder short-circuit, and rejects combination with `#[from]`,
  `#[datatable]`, `#[step_args]`, and placeholder-bound parameters with
  targeted diagnostics. Rationale: any path that does not strip the marker
  degrades into `cannot find attribute`, which is exactly the poor developer
  experience this roadmap item exists to remove. Date/Author: 2026-08-15,
  planning agent.

- Decision: `#[from(rstest_bdd_harness_context)]` is not deprecated in v0.6.1.
  Rationale: the roadmap requires "backwards-compatible support"; a deprecation
  warning in a patch-compatible release would force churn on adopters mid-beta,
  and the v0.7.0 line (roadmap 12.2.1) will supersede both spellings with typed
  extractors anyway. Date/Author: 2026-08-15, planning agent.

- Decision: record the change as a dated addendum to
  `docs/adr-007-harness-context-injection.md` rather than a new ADR. Rationale:
  ADR-007 is the record that established the reserved fixture key and the
  `#[from(...)]` request form. Adding a second, readable spelling of the same
  request is an amendment to that decision, not a new one. The documentation
  style guide reserves ADRs for hard-to-reverse choices; a new ADR-016 would
  fragment the harness-context record across two documents. Alternative
  available if the reviewer disagrees: promote the addendum to ADR-016 and mark
  ADR-007 as amended-by. Date/Author: 2026-08-15, planning agent.

- Decision: verification uses `rstest` unit tests, a `proptest` property, an
  equivalence assertion over generated token streams, `trybuild` compile-fail
  fixtures, and one end-to-end behavioural scenario. No `kani` and no `verus`.
  Rationale: the invariant introduced is a syntactic mapping from three source
  spellings onto one fixture key. There is no unbounded arithmetic, no state
  machine, and no ordering or concurrency property, so a bounded model checker
  would restate the property rather than test it, and a deductive proof would
  have nothing to discharge. A `proptest` property over generated parameter
  identifiers and spellings is the proportionate adversary. This choice is made
  under the "use your best judgement" latitude in the task brief and
  `AGENTS.md`. Date/Author: 2026-08-15, planning agent.

- Decision: adopt `googletest` and `pretty_assertions` as workspace
  dev-dependencies, and use them for the assertions in this work. Rationale:
  richer, more expressive assertions that state in high-level code what
  property is being checked, and that report what was actually wrong on failure.
  `matches_pattern!` names the enum variant and the offending field where
  `assert!(matches!(…))` reports only `assertion failed`;
  `err(displays_as(contains_substring(…)))` states "an `Err` whose message
  mentions X" in one expression and prints the real diagnostic when it does not;
  `pretty_assertions::assert_eq!` renders a structural diff where the contract
  under test *is* the equality of two values. Neither crate has been used in
  this workspace before, which is a reason to introduce them deliberately
  rather than a reason to keep deferring: a convention that is always postponed
  until it is already established never gets adopted at all. Milestone 2
  therefore introduces them as a named milestone with a documented vocabulary,
  so subsequent work has a precedent to follow. Rejected: continuing with bare
  `assert_eq!` and `assert!`. Every test here is expressible that way, but the
  failure output would name neither the property nor the actual value, which is
  the whole point. Date/Author: 2026-08-15, planning agent; confirmed by the
  maintainer 2026-08-15.

- Decision: enable `googletest`'s non-default `proptest` feature. Rationale: it
  converts a failing `verify_that!` into a
  `proptest::test_runner::TestCaseError` through `?`, so the property test uses
  the same matcher vocabulary as the unit tests instead of degrading to
  `prop_assert_eq!`. `googletest` 0.14.3 declares `proptest ^1.9.0` and this
  workspace pins `proptest = "1.9.0"`, so the requirement unifies without a
  second copy in the dependency graph. Date/Author: 2026-08-15, planning agent.

- Decision: compose with `rstest` as `#[rstest]` followed by
  `#[googletest::test]`, not `#[gtest]`. Rationale: `rstest` recognizes a
  following test attribute only when it is named `test`. `googletest::test` is
  an alias of `gtest` published for exactly this purpose, and the ordering is
  the composition documented upstream. Plain `#[gtest]` remains correct for
  tests that do not also use `#[rstest]`, and is required for `expect_that!`.

## Context and orientation

### What this repository is

`rstest-bdd` is a Rust behaviour-driven-development framework layered on the
`rstest` fixture-based test framework. A user writes Gherkin `.feature` files,
writes step functions annotated `#[given("…")]` / `#[when("…")]` /
`#[then("…")]`, and binds a test function to a scenario with `#[scenario(…)]`.

The workspace has nine library crates under `crates/` and four example crates
under `examples/`, all workspace members of the root `Cargo.toml`. The four
that matter here:

- `crates/rstest-bdd` — the runtime. Owns `StepContext`, the per-step fixture
  map, and step execution.
- `crates/rstest-bdd-macros` — the procedural macros. Parses step function
  signatures and generates wrapper functions. **May not depend on `rstest-bdd`
  .**
- `crates/rstest-bdd-policy` — small shared crate that both of the above depend
  on, existing specifically to break the proc-macro dependency cycle.
- `crates/rstest-bdd-harness` — the `HarnessAdapter` and `AttributePolicy`
  traits, plus test-staging helpers. A dependency of the macro crate and a
  *dev*-dependency of the runtime crate.

### Terms of art used in this plan

- **Harness adapter** — a type implementing
  `rstest_bdd_harness::HarnessAdapter`, which wraps scenario execution in a
  framework-specific runtime (Tokio, GPUI, …). It has an associated type
  `Context`, an object the harness constructs per scenario and makes available
  to steps.
- **Reserved fixture key** — the string `"rstest_bdd_harness_context"`, under
  which the framework inserts `HarnessAdapter::Context` into the `StepContext`
  fixture map. Defined at `crates/rstest-bdd/src/context/mod.rs:46` as
  `pub const RSTEST_BDD_HARNESS_CONTEXT_FIXTURE`.
- **Inert marker attribute** — an attribute such as `#[datatable]` that has no
  definition of its own. It is legal only because the enclosing attribute macro
  (`#[given]` and friends) removes it from the token stream before the compiler
  sees it. If a code path forgets to remove one, the compiler reports
  `cannot find attribute … in this scope`.
- **Classifier** — one of a chain of functions in the macro crate that inspects
  a step function parameter and decides what kind of argument it is: a step
  argument bound to a Gherkin placeholder, a fixture injection, a data table, a
  doc string, or a step-argument struct.
- **`trybuild`** — a crate that compiles fixture `.rs` files and compares the
  compiler's stderr against a committed `.stderr` snapshot. Used here for
  compile-fail diagnostics.

### The parameter classification pipeline

This is the code you will modify. Everything lives under
`crates/rstest-bdd-macros/src/codegen/wrapper/args/`.

The entry point is `extract_args` in `extract.rs` (line 157). For each
parameter of a step function, in order, it:

1. Calls `extract_step_struct_attribute` (line 165). If the parameter carries
   `#[step_args]`, `classify_step_struct` claims it and the loop moves on.
2. Computes `is_placeholder` — whether the parameter's name matches an unbound
   Gherkin placeholder (line 170).
3. **If and only if `is_placeholder` is false**, calls
   `classify_special_argument` (line 171), which tries `classify_datatable` then
   `classify_docstring`.
4. Otherwise falls through to `classify_fixture_or_step` (line 176), the
   terminal classifier. This one consumes any `#[from(...)]` attribute, then
   either claims a matching placeholder (producing `Arg::Step`) or records a
   fixture injection (producing `Arg::Fixture { pat, name, ty }`).

The output is an `ExtractedArgs` holding a `Vec<Arg>`. Codegen in
`arguments/fixtures.rs` (`gen_fixture_decls`, line 173) turns each
`Arg::Fixture` into a borrow against the step context:

```rust,ignore
#ctx_ident.borrow_ref::<#borrow_ty>(stringify!(#name))
```

So the *whole* mechanism by which `#[from(rstest_bdd_harness_context)]` works
today is: the user's identifier lands in `Arg::Fixture::name`, and `stringify!`
turns it back into the string the runtime looks up. Nothing in the macro crate
knows that this particular string is special.

Two shared helpers you will reuse:

- `extract_flag_attribute(arg, attr_name)` in `classify/mod.rs` (line 107).
  Strips every attribute whose path is `attr_name` from a parameter, returning
  whether one was present, and erroring on the argued form (`#[foo(1)]`) or a
  duplicate. Already used by `#[datatable]` and `#[step_args]`.
- `Arg::Fixture { pat, name, ty }` in `args/mod.rs` (lines 27-48). The variant
  you will construct, with `name` set to a synthesized
  `rstest_bdd_harness_context` identifier.

Existing precedent for rejecting attribute combinations:

- `DATATABLE_WITH_FROM_ERROR` in `classify/mod.rs` (line 50) plus its check at
  line 315.
- `validate_no_from_attr` in `classify/step_struct.rs` (line 99).

### Module layout convention

Commit `3e6c367` ("Adopt directory-based Rust modules", #651) moved every
module root that has children into a `mod.rs`. The rule the tree now follows:

- A module with child modules is a directory containing `mod.rs`.
- A leaf module is `<name>.rs` inside its parent's directory.

`classify` shows both halves. It is a directory containing `mod.rs` (the module
root, formerly `classify.rs`) plus the leaves `fixture_or_step.rs`,
`step_struct.rs`, `type_shape.rs`, `tests.rs`, and `prop_tests.rs`.

`harness_context` will have children — its own `tests` and `prop_tests` — so it
must be a directory with `mod.rs`, not a `harness_context.rs` sitting beside a
`harness_context/` directory. The latter is precisely the shape #651 removed.
The resulting layout:

```plaintext
crates/rstest-bdd-macros/src/codegen/wrapper/args/classify/
├── mod.rs                    <- add `mod harness_context;` here
├── fixture_or_step.rs
├── step_struct.rs

└── harness_context/
    ├── mod.rs                <- classify_harness_context lives here
    ├── tests.rs
    └── prop_tests.rs
```

No lint enforces this; it is a convention carried by the tree's shape, so a
reviewer will notice a violation before any gate does.

#### The assertion vocabulary this establishes

Record it in `docs/developers-guide.md` as a new subsection, and follow it in
Milestone 3. The point of these crates is that an assertion should say what
property is being checked, and a failure should say what was wrong — not merely
that two opaque values differed.

- **`googletest` matchers are the default for structural assertions.** Reach
  for `assert_that!` (fatal), `expect_that!` (non-fatal, requires the test to
  be marked `#[gtest]`), or `verify_that!` (returns `googletest::Result`,
  composes with `?`).
- **`matches_pattern!`** is the right tool for asserting on an enum variant and
  its fields at once. `assert!(matches!(x, Arg::Fixture { .. }))` reports only
  `assertion failed`; `matches_pattern!` reports which field mismatched and
  what it held.
- **`err(displays_as(contains_substring(…)))`** is the right tool for asserting
  on a `syn::Error`. It states "this is an `Err` whose rendered message
  mentions X" in one expression, and prints the actual message on failure.
- **`elements_are!`** for ordered container assertions,
  `unordered_elements_are!` where order is not part of the contract, `len`,
  `is_empty`, `contains`, and `each` for the obvious cases.
- **`expect_that!` under `#[gtest]`** where a test checks several independent
  properties of one value. All failures are reported in a single run rather
  than only the first.
- **`pretty_assertions::assert_eq!`** for whole-value equality where a coloured
  structural diff is what the reader needs — comparing two `Vec<Arg>`, or two
  generated token streams rendered as strings. Import it per module with
  `use pretty_assertions::assert_eq;`, which shadows the `std` macro for that
  module only.
- **`insta`** remains the tool for snapshots. Nothing here displaces it.

Composing with `rstest` requires the alias, not the primary attribute name:
`rstest` recognizes a following attribute only when it is named `test`, so write
`#[googletest::test]` rather than `#[gtest]`, and put `#[rstest]` first. This
is the composition documented upstream:

```rust,ignore
use googletest::prelude::*;
use rstest::rstest;

#[rstest]
#[googletest::test]
fn classifies_the_marker() -> googletest::Result<()> {
    verify_that!(1, eq(1))
}
```

A test using `expect_that!` must be marked `#[gtest]` (or
`#[googletest::test]`) and may return either `()` or `googletest::Result<()>`.
`#[should_panic]` composes with `#[gtest]`, but note it inverts the meaning of
a failing non-fatal assertion, so do not combine the two casually.

Validation: `make check-fmt && make lint && make test` green, plus one
throwaway smoke test proving `#[rstest] #[googletest::test]` compiles and runs
in this workspace. Delete the smoke test before committing. Commit.

needed to diagnose a wrong key.

```rust
    placeholders: &HashSet<String>,
) -> syn::Result<bool>;
```

Behaviour, in order:

1. `let via_marker = extract_flag_attribute(arg, "harness_context")?;` This
   strips every `#[harness_context]` and gives the argued-form and duplicate
   diagnostics for free.
2. If `!via_marker`, return `Ok(false)` — the parameter is somebody else's.
3. Reject the conflicting combinations, each with its own `const &str`
   diagnostic and a `syn::Error::new_spanned(arg, …)`:
   - a remaining `#[from]` on the parameter;
   - a remaining `#[datatable]` on the parameter;
   - a remaining `#[step_args]` on the parameter;
   - `placeholders.contains(&pat.to_string())`, naming the placeholder in the
     message.

   Four sequential guards will trip Whitaker's `conditional_max_n_branches`.
   Extract them into a small `validate_harness_context_marker` predicate helper
   returning `syn::Result<()>`, driven by a table of
   `(attribute name, diagnostic)` pairs, in line with `AGENTS.md`'s "use
   predicate functions for conditional criteria with more than two branches" and
   `docs/complexity-antipatterns-and-refactoring-strategies.md`.
4. Synthesize the fixture identifier and push the argument:

   ```rust
   // `HARNESS_CONTEXT_FIXTURE` is a compile-time constant that is a valid Rust
   // identifier; `classify::harness_context::tests` pins that invariant, so
   // `Ident::new` cannot panic here.
   let name = syn::Ident::new(rstest_bdd_policy::HARNESS_CONTEXT_FIXTURE, pat.span());
   st.push(Arg::Fixture { pat: pat.clone(), name, ty: ty.clone() });
   ```

   Using `pat.span()` keeps downstream borrow errors pointing at the user's
   parameter rather than at macro-internal tokens.
5. Return `Ok(true)`.

Wire it into `extract_args` in `extract.rs`, **before** the `is_placeholder`
computation at line 170:

```rust
if classify_harness_context(&mut state, arg, &pat, &ty, placeholders)? {
    continue 'args;
}
```

## Idempotence and recovery

Every step is re-runnable. The gate commands are read-only apart from the build
cache, and each writes to a fixed `/tmp` log path that is safe to overwrite.

`make fmt` and `TRYBUILD=overwrite` are the only commands that rewrite tracked
files. Both are idempotent, but review their diffs before committing —
`make fmt` reflows Markdown and can introduce MD039 and MD013 violations that
`make markdownlint` will then reject, so always run the lint after the format.

Recovery is per-milestone: each ends in its own gated commit, so
`git reset --hard HEAD` returns to the last known-good state and
`git revert <sha>` unwinds a single milestone.

If a partially applied milestone leaves the tree uncompilable, the fastest
route back is `git checkout -- <path>` on the specific files, not a wholesale
reset — the tests from earlier milestones are worth keeping.

Do not run test, lint, or format gates concurrently. This workspace relies on
Cargo's build cache and its package-cache lock; parallel runs thrash both. If
another Cargo job on this machine holds the lock, wait for it rather than
creating a separate cache.

Nothing in this plan writes outside the repository and `/tmp`. No cleanup is
required beyond removing `/tmp` logs, which is optional.
